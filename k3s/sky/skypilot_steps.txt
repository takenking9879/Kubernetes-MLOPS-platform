SkyPilot API Server -- Deployment Steps
=======================================
Generated: 2026-03-30

CONTEXT
-------
Deploys a persistent SkyPilot API server (Helm chart) with consolidation mode enabled.
In consolidation mode the jobs-controller thread runs inside the API server pod itself,
eliminating the cloud controller VM and SSH-based status polling (fixes returncode: 255).

All Airflow sky-runner KPO pods become lightweight HTTP clients via
SKYPILOT_API_SERVER_ENDPOINT (added to env-secret). Zero code changes to DAGs or
sky_runner.py -- the SkyPilot SDK picks up the env var automatically.

KEY LESSON (learned during deploy):
  The Helm chart ignores apiService.envFrom and apiService.command/args.
  It has its own tini-based startup script and dedicated credential values:
    runpodCredentials.enabled + runpodCredentials.runpodSecretName
    vastCredentials.enabled   + vastCredentials.vastSecretName
    awsCredentials.enabled    + awsCredentials.awsSecretName
  These create the correct credential files inside the pod automatically.


PREREQUISITES
-------------
- kubectl configured for the target cluster
- helm 3.x installed (helm version to verify)
- apache2-utils installed for htpasswd (sudo apt install apache2-utils)
- .env file in repo root with: AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY,
  AWS_DEFAULT_REGION, RUNPOD_API_KEY, VASTAI_API_KEY, MLFLOW_TRACKING_URI
- An S3 bucket for SkyPilot workdir (already set: s3://k8s-mlops-platform-bucket/sky-workdir)


STEP 1: Check chart schema before deploying (first-time only)
--------------------------------------------------------------
helm repo add skypilot https://helm.skypilot.co && helm repo update

helm show values skypilot/skypilot --version 0.12.0 > /tmp/sky-defaults.yaml
# Verify the following keys exist in the output:
grep -E "runpodCredentials|vastCredentials|awsCredentials|consolidation" /tmp/sky-defaults.yaml


STEP 2: Create per-provider credential secrets in the skypilot namespace
-------------------------------------------------------------------------
# The chart uses dedicated secrets per provider (NOT a combined secret).
# Secret key names must match exactly what the chart expects.

# Load vars from .env:
set -o allexport; source .env; set +o allexport

kubectl create secret generic runpod-credentials -n skypilot \
  --from-literal api_key="$RUNPOD_API_KEY"

kubectl create secret generic vastai-credentials -n skypilot \
  --from-literal api_key="${VASTAI_API_KEY:-$VAST_API_KEY}"

kubectl create secret generic aws-credentials -n skypilot \
  --from-literal aws_access_key_id="$AWS_ACCESS_KEY_ID" \
  --from-literal aws_secret_access_key="$AWS_SECRET_ACCESS_KEY" \
  --from-literal aws_default_region="${AWS_DEFAULT_REGION:-us-east-1}"

# Verify:
kubectl get secret -n skypilot | grep -E "runpod|vastai|aws"


STEP 3: Generate basic-auth credentials for the API server
-----------------------------------------------------------
WEB_USERNAME=skypilot
WEB_PASSWORD=<choose-a-strong-password>
AUTH_STRING=$(htpasswd -nb "$WEB_USERNAME" "$WEB_PASSWORD")
echo "Save AUTH_STRING: $AUTH_STRING"
# Also save WEB_PASSWORD -- needed for SKYPILOT_API_SERVER_ENDPOINT in Step 7.


STEP 4: Install (or upgrade) the SkyPilot Helm chart
-----------------------------------------------------
helm upgrade --install my-skypilot skypilot/skypilot --version 0.12.0 \
  --namespace skypilot \
  --create-namespace \
  --set "ingress.authCredentials=${AUTH_STRING}" \
  -f k3s/sky/helm/values.yaml

# Monitor rollout:
kubectl rollout status deployment/my-skypilot-api-server -n skypilot --timeout=300s

# If rollout fails, check events:
kubectl describe pod -l app.kubernetes.io/name=skypilot -n skypilot


STEP 5: Verify cloud providers are enabled
------------------------------------------
kubectl exec -n skypilot deployment/my-skypilot-api-server -- sky check

# Expected output should show:
#   RunPod: enabled
#   Vast: enabled
#   AWS: enabled
#   Kubernetes: enabled (in-cluster)

# Also verify consolidation mode (no cloud controller VM):
kubectl exec -n skypilot deployment/my-skypilot-api-server -- sky status --all 2>&1 | \
  grep -i controller || echo "No controller clusters -- consolidation mode active"


STEP 6: Health check
---------------------
kubectl port-forward svc/my-skypilot-api-service -n skypilot 46580:80 &
PF_PID=$!
sleep 2
curl -s -u skypilot:${WEB_PASSWORD} http://localhost:46580/api/health
kill $PF_PID
# Expected: {"status":"ok"} or similar


STEP 7: Add API server endpoint to Airflow pods
-------------------------------------------------
# The SKYPILOT_API_SERVER_ENDPOINT env var makes all sky-runner KPO pods act as
# HTTP clients to the centralized API server. All KPO pods already use
# envFrom: secretRef: env-secret, so adding this to .env is all that's needed.

# Get the internal service name (verify it matches what's in this command):
kubectl get svc -n skypilot

# Append to .env:
cat >> .env << EOF

# SkyPilot API server endpoint (added $(date +%Y-%m-%d))
SKYPILOT_API_SERVER_ENDPOINT=http://skypilot:${WEB_PASSWORD}@my-skypilot-api-service.skypilot.svc.cluster.local
EOF

# Refresh env-secret in airflow namespace:
kubectl create secret generic env-secret -n airflow \
  --from-env-file=.env \
  --dry-run=client -o yaml | kubectl apply -f -

# Verify the key is present:
kubectl get secret env-secret -n airflow -o jsonpath='{.data.SKYPILOT_API_SERVER_ENDPOINT}' \
  | base64 -d && echo


STEP 8: Update Prometheus scrape config
-----------------------------------------
# prometheus-stack.yaml already has the skypilot-api-server scrape job.
# Verify the service name/port from Step 7, update if needed, then:

kubectl rollout restart deployment/prometheus -n monitoring

UPGRADE PROCEDURE (after values.yaml changes)
=============================================
helm upgrade my-skypilot skypilot/skypilot --version 0.12.0 \
  --namespace skypilot \
  --set "ingress.authCredentials=${AUTH_STRING}" \
  -f k3s/sky/helm/values.yaml

# To update credentials only (no helm upgrade needed):
kubectl create secret generic runpod-credentials -n skypilot \
  --from-literal api_key="NEW_KEY" \
  --dry-run=client -o yaml | kubectl apply -f -
# API server restart is triggered automatically.


TROUBLESHOOTING
===============

Problem: sky check shows cloud providers not enabled
-----------------------------------------------------
1. Verify credential secrets exist in skypilot namespace:
     kubectl get secret -n skypilot
2. Verify secret keys match what chart expects:
     kubectl get secret runpod-credentials -n skypilot -o jsonpath='{.data}' | python3 -c "import sys,json,base64; d=json.load(sys.stdin); [print(k, base64.b64decode(v).decode()[:8]+'...') for k,v in d.items()]"
3. Verify values.yaml has runpodCredentials.enabled=true and correct secretName.
4. Check pod logs for credential-related errors:
     kubectl logs -n skypilot deployment/my-skypilot-api-server | grep -i "cred\|auth\|key\|runpod\|vast\|aws"

Problem: Helm upgrade fails or values are ignored
--------------------------------------------------
Run: helm show values skypilot/skypilot --version 0.12.0 | grep -E "runpod|vast|aws|consolidation"
Ensure the key names in values.yaml match exactly (case-sensitive).

Problem: Airflow pods still start a local API server
------------------------------------------------------
1. Confirm env-secret has the key:
     kubectl get secret env-secret -n airflow -o jsonpath='{.data.SKYPILOT_API_SERVER_ENDPOINT}' | base64 -d
2. If missing, re-run Step 7.
3. Restart Airflow scheduler:
     kubectl rollout restart deployment/airflow-scheduler -n airflow

Problem: Prometheus target shows DOWN
--------------------------------------
1. Confirm service name and port: kubectl get svc -n skypilot
2. Check metrics endpoint: kubectl port-forward svc/my-skypilot-api-service -n skypilot 9090:9090 &
   curl http://localhost:9090/metrics | head -20; kill %1
   (Note: metrics may be on port 9090, not 46580 — check svc output)
3. Update prometheus-stack.yaml target if service name/port differs.
