Spot-First Strategy (Applies to All Phases)
Default behavior: Every job uses spot instances first, on-demand only as last-resort fallback.

SkyPilot any_of pattern (spot-first):

resources:
  any_of:
    - accelerators: A100:1
      use_spot: true      # cheapest, almost always wins
    - accelerators: A100:1
      use_spot: false     # fallback if no spot available
SkyPilot selects the cheapest option — spot will win if available (70–90% savings).

SkyPilot spot recovery vs Ray FailureConfig — they operate at different levels:

SkyPilot (retry_until_up=True or managed jobs): handles infrastructure failures — spot preemption → re-provision node → restart job. This is the primary recovery mechanism.
Ray FailureConfig: handles application-level worker failures within a running cluster (OOM crashes, driver timeouts). Complementary, not redundant.
For spot recovery specifically: use sky jobs launch (managed jobs) instead of sky launch for automatic preemption handling and cross-region retry. sky launch --retry-until-up handles provisioning retries but not mid-job preemptions.
Decision rule for DAG: Use sky.jobs.launch() for training jobs (handles spot preemption) vs sky.launch() for serving (persistent cluster, no preemption tolerance needed).

Cross-region failover: SkyPilot auto-failover activates automatically — if a region has no capacity, it retries other regions in the same cloud, then other clouds. No extra config needed beyond the any_of list ordering.

@dataclass
class ResourceConstraints:
    providers: list[str]
    gpu_types: list[str] | None   # None = cheapest available
    min_vram_gb: int = 0
    max_price_per_hour: float = 9999
    prefer_spot: bool = True      # DEFAULT True (spot-first)
    require_infiniband: bool = False
    preferred_regions: list[str] = field(default_factory=list)
    num_nodes: int = 1
    num_gpus_per_node: int = 1
    job_type: str = "tabular"     # "tabular" | "llm"
Scoring algorithm (produces ordered any_of list — spot entries first):

Filter: wrong provider, below min_vram, infiniband required but unavailable
Generate two entries per valid offer: spot variant + on-demand variant
Score spot: price_spot * 1.0 (if spot_available=True); deprioritize if unavailable
Score on-demand: price_on_demand * 2.5 (price premium to always prefer spot)
Region bonus: score *= 0.95 for preferred regions
InfiniBand bonus: score *= 0.85 if required and available
Sort ascending by score → spot entries naturally bubble up
Deduplicate: same cloud+gpu can appear once (spot) before its on-demand fallback
Append final "any cloud, any GPU matching VRAM" spot+ondemand entries as last resort
Output order example for RTX2000-Ada on RunPod:

1. {cloud: runpod, accelerators: RTX2000-Ada:1, use_spot: true}   # cheapest
2. {cloud: runpod, accelerators: RTX4090:1, use_spot: true}       # next cheapest spot
3. {cloud: vast, accelerators: RTX3090:1, use_spot: true}         # alternative spot
4. {cloud: runpod, accelerators: RTX2000-Ada:1, use_spot: false}  # on-demand fallback
5. {cloud: runpod, accelerators: RTX4090:1, use_spot: false}      # on-demand fallback

Spot Recovery Architecture (clarified)
Two-level recovery:

SkyPilot managed jobs (sky jobs launch): node preempted → SkyPilot auto-provisions new node in another region, restarts the entire job from scratch (or from last checkpoint if S3 storage_path set)
Ray FailureConfig: within a running cluster, handles worker-level failures (OOM, crash) by restarting from last Ray Train checkpoint saved to storage_path
Both are complementary. For cost-optimized spot training, add FailureConfig so transient worker crashes don't restart from epoch 0.

Grafana/Prometheus Architecture Change
The existing K8s Grafana + Prometheus works for KubeRay jobs (pods running inside the cluster on Docker Desktop kubeadm). In-cluster Prometheus also remote_writes existing Ray/K8s metrics → Grafana Cloud
Single Grafana Cloud dashboard shows both sources

# app/backend/services/orchestration_selector.py

def select_training_orchestration(model_type: str) -> str:
    if model_type in ("ann", "ssm", "bae", "xgboost", "user_uploaded"):
        return "ray_train"          # existing tabular pipeline
    elif model_type == "llm":
        return "llm_finetune"       # HF+TRL+DeepSpeed (llm_main.py)

def select_serving_orchestration(
    model_vram_gb: float,
    num_gpus_per_node: int,
    vram_per_gpu_gb: float,
    num_nodes: int,
) -> str:
    fits_single_node = model_vram_gb <= num_gpus_per_node * vram_per_gpu_gb
    if fits_single_node and num_nodes == 1:
        return "vllm_single_node"   # vllm-serving.yaml (simpler, cheaper)
    else:
        return "ray_vllm_multinode" # Kimi-K2 pattern: Ray+vLLM (tensor+pipeline parallel)
Kimi-K2 pattern for multi-node LLM serving:

Head node: ray start --head + vllm serve with --tensor-parallel-size=GPUs_per_node --pipeline-parallel-size=num_nodes
Worker nodes: join Ray cluster, sleep (Ray handles work routing)
network_tier: best in YAML for InfiniBand/EFA when available
Use sky status --endpoint 8081 <cluster> to get the endpoint URL

SkyPilot Provides vs What We Build
SkyPilot provides:

Infra provisioning + spot-first via any_of with use_spot ordering
Cross-region failover (automatic, no config needed)
Managed jobs (sky jobs launch): auto-restart on spot preemption
retry_until_up=True for provisioning retries
idle_minutes_to_autostop for cost safety
sky.list_accelerators() for offline GPU catalog
SKYPILOT_NODE_RANK, SKYPILOT_NODE_IPS, SKYPILOT_NUM_NODES env vars
MOUNT_CACHED for persistent overlays
We build:

Real-time spot availability from RunPod + Vast APIs (SkyPilot catalog is cached/static)
Spot-first scoring algorithm with price comparison (spot vs on-demand)
Dynamic any_of YAML generation from user constraints
GPU metrics push to Prometheus (SkyPilot has no built-in metrics)
Per-run cost tracking with is_spot label in MLflow
LLM model catalog with GPU/VRAM recommendations
vLLM serving lifecycle management (persistent cluster, endpoint registration)
UI cost comparison table (spot price vs on-demand side-by-side)
